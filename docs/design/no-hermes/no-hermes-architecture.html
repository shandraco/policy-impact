policy-impact · design proposal · no-Hermes option

One assistant for policies,
documents and spreadsheets

20 October 2026 · Draft for discussion · An alternative to the Hermes-based policy-impact build

The scope grows from comparing policies to helping staff write policies, build documents and spreadsheets, and edit them in the tools they open every day. For that scope we propose dropping Hermes and running one assistant of our own, built with LangGraph, that is also the Overwatch. Staff work in a chat window and in a document editor, and every change the assistant suggests is shown first and applied only when a person accepts it.

Decisions in this proposal

  • One agent, not two layers. Our own LangGraph graph understands the request, calls tools, checks the result and asks for approval. The tool gate and answer checks are part of it, not a guard around someone else's agent.
  • The model suggests; code makes the change; a person accepts. The v0.1 rule that code builds every answer now covers editing too. The model never writes a file directly.
  • A document editor next to the chat. Staff open, view and edit Word and Excel files in a self-hosted browser editor, with an optional assistant pane inside desktop Word and Excel later.
  • Use cases are packs. Policy impact, policy writing, documents, spreadsheets and each outside tool are separate packs with their own tools, checks and approval rules.
  • Everything stays on the sealed network unless the client decides that Microsoft 365 is allowed.

Why drop Hermes for this scope

  • The control is the real work. The tool gate, checks, approvals and audit would be built anyway. Without Hermes they become the assistant instead of a fence around a large, weekly-released codebase that is not being reviewed.
  • Knowing who is asking is built in. No signed-token workaround is needed to tell tool calls which person and chat they belong to.
  • Outside tools become safe to add. Each connector (an MCP server or a small adapter) is a tool behind our own gate, switched on per pack and per user.
  • Less to lock down. No Hermes settings list, no read-only config checks, no stray outbound calls to switch off.
What we give up. Hermes provides a ready-made agent loop, chat-title and housekeeping tasks, and an OpenAI-compatible API. A LangGraph agent loop is a small amount of code, and the OpenAI-compatible endpoint is a thin FastAPI layer, so the cost is a few days of build, paid back in a smaller system we fully understand.

System architecture

Everything below the proxy runs on the client's GPU server under Docker Compose, on internal networks with no route to the internet. Staff reach three front ends through the proxy; all three talk to the same assistant.

Recommendation

  • ONLYOFFICE Docs Community 10.0, self-hosted on the sealed network, for the pilot. Free, unlimited connections, closest to Word and Excel.
  • Keep our own docs-api as the way edits are applied, so the assistant does not depend on the editor's AI plugin.
  • Move to ONLYOFFICE Enterprise only if the client wants vendor support or features the free edition lacks.
  • Collabora is the fallback if a spike below fails.

Rest of the stack, checked

  • LangGraph 1.2.16 (16 Oct 2026), MIT licence; Postgres checkpointer 3.2.0. Tracing is off unless LANGSMITH_TRACING=true is set.
  • Open WebUI 0.12.3 takes any OpenAI-compatible endpoint. Keeping its branding avoids the licence's 50-user limit on rebranding.
  • vLLM 0.32 runs gpt-oss-120b tool calls with --tool-call-parser openai --enable-auto-tool-choice. A reported parser issue (#58825) can turn stray text into a fake tool call; the gate must reject unknown tool names.
  • Office add-in: Word's tracked-changes API exists, but offline loading of office.js and IT deployment paths are unverified. Kept for after the pilot.

What carries over from policy-impact

  • Keep: the impact pipeline, Postgres with row-level security, the review page, signed downloads, the evaluation set, the containment scripts and internal networks.
  • Becomes part of the assistant: the model gate (approved prompt, temperature 0, one tool call at a time) and the user scope from Open WebUI, now passed directly instead of through a signed token in the chat.
  • Removed: the Hermes container, its plugin, its read-only configuration and its checksum service.

Tests before the pilot

  1. Same verdicts: impact results match the current build on the evaluation cases.
  2. No silent edits: no file changes without an Accept, and Undo always leaves the file as it was.
  3. Numbers: every total in a generated or edited workbook recomputes to the same value; no formula results typed in by the model.
  4. Sources: every policy id and section cited exists; documents contain no names, dates or amounts that were not supplied.
  5. Access: a user cannot see or edit another unit's policies or files (row-level security and file store both checked).
  6. Containment: no connection leaves the server from any container, the editor included.
  7. Runaway: a request built to loop stops at the budget with a clear message.
  8. No-help test: a staff member writes a short policy, builds a workbook and accepts an edit without help.

Check first, and open questions

  • Where do staff edit today: desktop Word and Excel, Microsoft 365 online, or both? This picks the front end.
  • Can data live in Microsoft 365? If not, option 3 is off the table.
  • Editor licence: confirm OnlyOffice's Community terms (attribution and labelling of modified versions) with counsel, or budget for its Enterprise edition if support is needed.
  • LangGraph agent helpers: LangChain 1.x presents create_agent with approval middleware; whether to use it or a hand-written graph is decided in spike 4.
  • Model reliability: measured in spike 4 before the main build.
  • Which outside tools first: name the first one or two connectors so their packs can be designed.
